## Design decisions and invariants

### Secondary-index architecture

```text
current ──atomic──> Version { segments[256]              primary directory
                              index_offset, index_len
                              isegs[64] }                 secondary-index directory
                                  └──> IndexSegment = header | buckets[] | pairs[]   (one allocation, immutable)
```

- One index per store over value bytes `[offset, offset + len)`.
- An index segment holds every (field hash, primary key) pair of one of 64 hash partitions,
  sorted by (hash, key): the keys of one field value are contiguous and ascending, a posting
  list. A linear-probing bucket table over the distinct hashes points at each list.
- It stores hashes and keys only, so it owns nothing else, and the hash never decides a
  match: every candidate key is checked byte for byte against the primary data of the same
  version.
- A custom structure; no library container.

### Index creation and backfill

`create_index` validates the range, scans the current version's values, builds all index
segments privately, and publishes a new version that shares every primary segment and points
at the new index: one swap. Until then nothing of the index is reachable.

| Case | Result | Tested |
|---|---|---|
| Empty store | `true`; later writes indexed | yes |
| Populated store (backfill), duplicates | `true`; one publication; no primary segment copied | yes |
| Embedded zero bytes | ordinary bytes | yes |
| Short values, zero-length values | stored, **not indexed**, nothing read beyond the value | yes |
| Invalid offset / length (0, beyond 1 GiB, overflow) | `false`, nothing published | yes |
| Repeated call, same range | `true`, nothing published | yes |
| Repeated call, different range | `false` | yes |
| Concurrent readers | lookups see no index or the complete one, never part | yes |
| Concurrent writer | serialized by the writer mutex; index stays in step afterwards | yes |
| Existing snapshots | keep their index-less version | yes |
| Allocation failure during construction | `false`, no index, store unchanged | 19 failure points |

### Atomic primary/index publication argument

A commit, with the writer mutex held: (1) applies its operations to private copies of the
touched primary partitions, and for each operation compares the key's indexed field before and
after **in the private copy**, recording index deltas; (2) allocates everything else and
builds, privately, the replacement for every index partition the deltas touch; (3) *from here
nothing can fail*: assembles the new `Version` with the replaced primary segments, the
replaced index segments and shared pointers to everything else; (4) executes the one
`current.exchange(next)`.

`current` is written once, and what it is given already contains both the rows and the index
that describes them. A reader loads the root once: before the exchange it has the old rows
with the old index; after it, the new rows with the new index. No third state exists, for one
key or for a hundred. All allocations precede (3), so a failure frees private objects only;
no owner count has changed and the root is untouched. There is no separate index publication
and no index update outside a commit.

### Snapshot-aware index lookup

`index_get(snap, …)` takes the `Version*` remembered in the snapshot's reader slot and reads
that version's index segment, then that version's values for the byte check. It never loads
`current`. The plain overload runs the `get` protocol (announce, validate, one root load) and
does the same on the version it loaded. Wrong-store and moved-from handles are rejected by
the owner comparison before anything is dereferenced.

### Index node ownership and reclamation safety

- `IndexSegment::owners` counts the versions pointing at the segment: `store(1)` when a new
  one is attached to the version being built, `fetch_add(1)` when shared with the current
  version (which holds a reference and can only be retired later, by this same commit),
  `fetch_sub(1)` by the cleaner in `run_job`, after the version passed the epoch test. The
  decrement to zero frees. This is the argued rule of `docs/reclamation.md` §5.4 with one more
  object type.
- Published segments are never modified; a segment references nothing, so freeing it has no
  consequence for chunks or chunk IDs.
- A snapshot pins a version; a pinned version is not destroyed; so its primary segments, its
  index segments and the chunks its primary segments list all keep a non-zero count, in all
  three reclamation modes.
- `validate()` recomputes, for every existing version, the pairs the primary data implies and
  requires the index to hold exactly those; it checks segment structure and every owner count.

### Join implementation

`benchmarks/join.h`, public API only: (1) `keys()` on the outer table under the outer
snapshot; (2) `get()` of each outer row under the outer snapshot; (3) the row's join field;
(4) `index_get()` on the inner table under the inner snapshot; (5) `get()` of each matching
inner row under the inner snapshot; (6) emit. Buffers for keys and matches are enlarged and
the call repeated when one comes back full, so nothing is silently truncated. Records of the
wrong size are skipped and counted.

### Option A: the exact snapshot guarantee and its limitation

The join acquires **one Snapshot from each store** in `acquire_join_snapshots`, at its very
start, and holds both to the end. Each handle is used for every call on its own store. No
other snapshot is acquired and no current-version read is made inside a join.

Guaranteed:

- Trades is read from one immutable version;
- Instruments, rows and index, is read from one immutable version;
- each table is internally consistent for the whole join;
- writers keep publishing and are never blocked.

**Not guaranteed, and not claimed:**

- the two snapshots are not one globally atomic point in time. If both tables are written
  during joins, a join can combine versions of the two tables from different moments;
- the implementation uses **two handles, not the assignment's literal "exactly one Snapshot
  handle"**. This is a deviation from the PDF's wording.

No global cross-store versioning was introduced, and the tables were not merged into one
store.

Observations, with their limits:

- **A join costs about twice as much with the writer active** (p50 6.5 → 15.4 ms at one
  joiner; 7.8 → 14.0 ms at eight). Throughput still scales with joiners (64 → 553 joins/s
  from 1 to 8). Why it is twice is not established: no profiler. Candidate causes are the
  writer's updates of owner counts on cache lines the readers load (audit item R8, still
  open, now also for index segments) and memory traffic from copying.
- **The same pattern for `index_get`:** about half the throughput with a writer running flat
  out next to it (21.3 → 9.8 M/s at one thread), p99.9 still 0.25 µs.
- **Joins hold reclamation back while they run.** Each join pins both stores for its
  duration (7–25 ms), so everything retired meanwhile waits: up to 158–365 MiB held and a
  backlog of 5,800–18,600 versions with the writer active, against 9.1 MiB idle. It drains
  completely afterwards (validated in every run). This is the cost of long snapshots stated
  in C1, here with numbers.
- **The index is cheap to read and expensive to change on a big low-cardinality table.**
  Changing a Trade's symbol rebuilds two index partitions, about 114 KB, and single-key writes
  drop to about a fifth (234,906 → 49,432/s). With the index present but the field unchanged
  the writer still loses about a third (158,664/s): field comparison, delta buffer, 64 more
  owner references per commit. For the table the assignment indexes (Instruments, 50 rows)
  none of this is significant: the writer rewrote it 2,671 times per second in whole-table
  transactions during the join runs.
- Backfill is about 100 ns per row.
- 100k+ RPS: `index_get` and joined rows per second are far above 100,000/s in every
  configuration; the Part D statement still needs the D.1 protocol on point gets.

## Profiling bottlenecks and next hypotheses

No profiler could be run. From counters only, to be tested in Part D:

- Owner counts (`Segment::owners`, `IndexSegment::owners`) share cache lines with fields that
  every reader loads; a writer increments 255 + 64 of them per commit. Suspected in the 2×
  slowdown of reads next to a writer.
- Index maintenance copies whole partitions; a posting-list layout that shares unchanged
  lists between versions would reduce 114 KB per field change to the changed list.
- `acquire_snapshot` takes the registration mutex twice per join; irrelevant at 7 ms per join.
- The join does two lookups per record to check its size (`exact_row_sizes`); the benchmark
  measures that tested path.

## Known limitations and source ambiguities

Architectural deviations and their reasons:

1. **One Snapshot per store in the join (D-060, your decision).** Deviation from the PDF's
   "exactly one Snapshot handle"; not claimed as compliant.
2. **The join lives in `benchmarks/join.h`, over the public API**, not inside the store:
   Appendix A has no join entry point (D-064).
3. **Index segments store hashes, not field bytes**, and every match is verified against the
   primary data. The blueprint spoke of an index "keyed by canonical copied field byte
   sequence"; storing no bytes means an index segment owns nothing and needs no new reference
   type (D-061).
4. **Values too short for the field are stored and not indexed**, where the blueprint
   suggested requiring them to cover the range (D-062).
5. **64 index partitions**, not 256.
6. **No index on the lock baselines** (D-063).

Limitations:

7. A write that changes the indexed field rebuilds whole index partitions (measured above).
8. One index per store; no index removal; exact-match probes of the full field only.
9. `index_get` does one primary lookup per candidate.
10. Joins, like any long snapshot, hold back reclamation for their duration.
11. Isolation as stated in C1: no read set, no validation; lost updates and write skew are
    possible; no durability.
12. The supplied generator's `use_join` probe passes an 8th symbol byte that the generator
    never writes, so by the language it may miss on a byte-exact index (D-065); it is not a
    join in any case. *(C2 audit: measured afterwards, the byte is 0 in every build here and
    the probe matches 100 %; `results/C2_audit/generator_probe_hit_rate.txt`. "May miss" is
    what the source permits, not what these binaries do.)*
13. A leak was found by review and fixed in this milestone (D-066); the engine-only path it
    was on had no test before.
14. `reclamation_stress_test` keeps scheduling-dependent coverage floors (D-056): run the
    suite serially.
15. The safety argument is manual. GCC 15.2 only. No profiler.
