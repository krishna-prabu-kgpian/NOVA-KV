## Design decisions and invariants

### Transaction

`put()` copies the value into the transaction's own write set at once and never references
the caller's buffer again. `commit()` turns the set into one array of operations and calls the
engine function a single `put` uses: one private copy per touched partition, one new
`Version`, **one `current.exchange`**. That exchange is the linearization point of the whole
transaction.

| Case | Behaviour |
|---|---|
| Several puts to one key | last one wins |
| Empty commit | `true`, nothing published |
| Second commit | `false`, nothing published |
| `put` after commit | ignored |
| Unstageable put (no memory, null with a length, above 1 GiB) | `commit()` returns `false`, nothing published |
| Allocation failure in commit | `false`, store unchanged |
| Destroyed uncommitted | discarded, memory freed |

Lock baselines: the staged writes are applied under one exclusive lock hold and undone if a
step fails (replaced values stay allocated until the batch has succeeded). Atomic and
all-or-nothing, but not a pointer swap.

### Snapshot

One long-lived reclamation pin. `acquire_snapshot()` takes a dedicated reader slot, announces
and validates an epoch, then loads the root once. The handle's `void*` is the slot; the slot
remembers the version. Snapshot-scoped calls use that version and never load the root.
Destruction clears the announcement and returns the slot.

- **Lifetime.** To the reclamation scheme a snapshot is a reader that has not finished, so
  Theorem 1 of `docs/reclamation.md` applies unchanged: nothing retired since its acquisition
  becomes eligible while it lives; the segments, chunks and chunk IDs reachable from it stay.
- **Move.** Copies two words and clears the source; the slot is not written. No moment
  without protection, no second owner.
- **Cost of holding one.** Reclamation of everything retired afterwards stops until release.

### Stop-the-world comparator correction

Before: once it held the exclusive lock (excluding every `get`), it freed the entire retire
list. A pin holds no lock between calls and was not consulted; a snapshot's version and
chunks could be freed under it. Reproduced before fixing
(`results/C1/stw_pin_reproducer_before_fix.txt`: 3000 versions freed under a pin, chunk IDs
reused, pinned values no longer intact).

Now: under the same freeze it makes two gated epoch advances and frees every entry the
eligibility rule `[C6]` allows, with no batch limit and no work budget. Short readers are
frozen out, so only pins can hold an entry back. It is still a whole-list sweep that stops all
readers (snapshot-scoped calls take the shared lock per call in that mode). **Every
destruction of a retired version outside the destructor now passes the same epoch test, in
every mode.**

### Owner validation

`get(snap, …)` and `keys(snap, …)` compare `snap.owner_` with `this` before touching anything.

| Handle | `get` | `keys` |
|---|---|---|
| from this store, live | pinned version | pinned version |
| moved-from | `false`, buffer untouched | `0`, buffer untouched |
| from another store | `false`, buffer untouched | `0`, buffer untouched |

A handle that outlives its store is the caller's error (shutdown contract) and is not
detected.

### Writer contract

All three write entry points end in `VersionedStore::commit`, whose writer state is
unsynchronized by design; two at once would corrupt it. They now hold one writer mutex for
their whole duration. Calls from several threads are safe and run one at a time, each as one
atomic publication. This is serialization, not concurrent writing, and it gives no isolation
between clients that read and then write. No read path takes the mutex. Staging takes no lock.

### Isolation actually provided

Atomic, serialized commits with snapshot-consistent reads. A snapshot is exactly one
committed state of one store. The `Transaction` interface has no reads and commit validates
nothing, so a read followed by a commit is not an isolated transaction: lost updates (weaker
than textbook snapshot isolation) and write skew are possible, whether the writes come from
one thread or several. No durability: a commit that returned `true` is lost if the process
dies. `docs/transactions.md` §5–§6.

*(Corrected by the C1 audit, decision D-057. The report as tagged at `part-c-transactions`
said here that "under the assignment's single writer every execution is serializable". That
was too strong: serializing commits says nothing about the reads a client based them on.)*

Invariants: INV-03 (one visibility point per commit), INV-07 (reclaim only when EBR proves no
reader or snapshot can reach it), INV-13 (a snapshot resolves every lookup through its
original root) are tested directly.

## Known limitations and source ambiguities

Architecture deviations and their reasons:

1. **Writer mutex** (D-053). The blueprint assumes one application writer; you asked for a
   writer-only serialization mechanism. Readers are unaffected.
2. **Stop-the-world comparator frees by the epoch rule** (D-051). It is no longer "free
   everything under the lock"; with no snapshot alive it behaves as before.
3. **`acquire_snapshot()` throws on the lock baselines** (D-055) instead of returning an inert
   handle. `Transaction` is implemented there, which the blueprint did not require.
4. **The version pointer lives in the reader slot** (D-054), so the public handle needs no
   allocation of its own.
5. **`transaction.cpp` / `snapshot_test.cpp` layout**: the blueprint's file list names
   `transaction.cpp`; the public classes are in `kvstore.cpp` (Appendix A: "defined in
   kvstore.cpp") and the write set in `staged_writes.cpp`.

Limitations:

6. No conflict detection: not serializable, and weaker than snapshot isolation for
   read-then-write clients. No durability.
7. A long-lived snapshot stops reclamation of everything retired after it; memory grows
   until it is released.
8. `keys()` cannot report the total or continue; the caller must size the buffer (O-18).
9. A snapshot must be destroyed before its store; a handle is for one thread at a time.
   Neither is checked.
10. Writers are serialized: no parallel write throughput.
11. `Snapshot` only on the `rcu` build.
12. `reclamation_stress_test` (a Part B test) has scheduling-dependent coverage assertions
