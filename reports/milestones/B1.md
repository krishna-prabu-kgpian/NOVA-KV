## Scope completed

Blueprint §8.5, nothing beyond it:

- A fourth build of `KVStore`, `rcu`, in which every successful `put`/`erase` builds its new
  state privately and publishes one immutable version with a single atomic pointer swap.
- `get` on that build: one `seq_cst` load of the root, then only immutable objects; no lock,
  no allocation, no shared write, no waiting.
- Copy-on-write index: only the segments a write touches are cloned; the rest are shared
  between versions.
- An internal multi-key commit (one clone per touched segment, one publication). The public
  `Transaction` is still Part C.
- Chunk ownership redesigned for multiple live versions (user decision D-023): segments pin
  the distinct chunks they reference; versions own segments.
- A global chunk directory readable without a lock; per-commit arena rollback.
- **Reclamation deliberately absent.** Every replaced version is retained until the store is
  destroyed.

Not done, by instruction: EBR, epoch slots, a cleaner thread, `set_reclaim_batch` (still
inert), `Transaction`/`Snapshot`/secondary index/join, WAL, the Part D campaign, performance
tuning, the submission ZIP.

## Design decisions and invariants

Full description: `docs/versioning.md`. Summary of the architecture as built:

```text
current ──atomic──> Version { sequence, segments[256] }           immutable
                        └──> Segment { slots[capacity], pins[], owners }   immutable, shared
                                 slot = { key, ValueRef{chunk_id, offset, length}, state }
chunk directory: blocks[1024] ──atomic──> block[1024] ──atomic──> chunk bytes (append-only)
```

**Commit** (`VersionedStore::commit`; `put` and `erase` are batches of one):
validate → group by partition, one private builder per touched partition → apply operations
in order, appending value bytes beyond every published reference → allocate segment headers,
the Version and the retirement node → *(nothing can fail from here)* → take chunk pins and
segment owner references → `current.exchange(next, seq_cst)` → hand the old version to the
retained list.

**Publication invariants**

| ID | Invariant | How it is established | Test evidence |
|---|---|---|---|
| INV-01 | Published Version, Segment and value bytes never change | Builders work on private copies; arena appends go past every published reference; no writable-chunk rewind | `versioned_store_test::test_old_versions_never_change` (logical and byte-for-byte), `cow_segment_test::test_base_is_untouched`; mutations B4, B11 |
| INV-02 | Only the writer stores to `current` | One store site (`commit`) | code inspection; B15 |
| INV-03 | One successful logical write = exactly one store to `current` | Single `exchange` after all building | publication counters in `versioned_store_test`, interleaving S3/S4; B13, B15 |
| — | A reader sees the complete old or the complete new version | All initialization sequenced before the `seq_cst` exchange; nothing new is reachable before it | interleaving S3, S4, S5; B3 |
| INV-10 | A failed commit publishes nothing and leaves no trace | All fallible steps precede any ownership change; arena rollback; builders own their allocations | `versioned_alloc_failure_test`; B6, B7 |
| INV-15 | No internal pointer escapes | `get` copies under the loaded version | buffer-guard checks in `kvstore_test_rcu` |

**Ownership invariants** (recomputed from scratch by `VersionedStore::validate()`)

| ID | Invariant |
|---|---|
| O1 | `segment.owners` = number of existing versions (current + retained) pointing at it |
| O2 | `segment.pins` = exactly the distinct chunks its occupied slots reference, with per-chunk entry counts, sorted |
| O3 | `chunk.pins` = number of existing segments listing the chunk (INV-05) |
| O4 | An unpinned chunk exists only if it is the writable chunk |
| O5 | Every `ValueRef` lies inside the written part of an existing chunk with that ID (INV-06) |
| O6 | Retained versions = publications − releases; bytes held match the objects that exist |

Why chunk-ID reuse is safe: a chunk is freed, its slot nulled and only then its ID recycled,
and only when it has no pin, is not the writable chunk and is not used by the commit in
progress. A reader reaches a chunk only through a segment of the version it loaded, and that
segment holds a pin as long as it exists. So reader safety reduces to "the version a reader
loaded still exists".

**Temporary lifetime strategy (B1).** That last condition holds trivially because nothing is
released while the store is in use: every replaced version stays on a writer-owned list (its
node is allocated before publication, so the hand-over cannot fail or lose a version) until
the destructor. Readers therefore need no protection in B1. Two internal hatches release
retained versions under the caller's promise that no other thread reads the store; they are
used by single-threaded tests and by the benchmark harness after its load phase, are not
reachable through the public API, and are not a reclamation protocol (D-032).

**Memory ordering.** Every atomic operation is `seq_cst` (root, directory blocks and slots,
`owners`, `pins`). Justification in `docs/versioning.md` §4. Nothing was relaxed.

**EBR.** Not introduced. The place where the reader's announcement must go (before the root
load) and where the retirement epoch must be sampled (after the exchange) are marked in
`versioned_store.cpp`. No simplified or partial epoch scheme exists in the code.

### Allocation-failure tests

`versioned_alloc_failure_test` retries each of 174 logical writes (single puts including the
first write into an empty store, growth of one partition 16 → 128 slots, chunk rollover,
oversized values, a zero-length value, a 15-operation batch across at least 13 partitions, 50 erases
including a partition erased to empty) with the 0th, 1st, 2nd … allocation failing until one
attempt meets no injected failure.

| Mode | Writes completed | Injected failures, all rolled back | Arena rollbacks | Tolerated in erase |
|---|---:|---:|---:|---:|
| Retain (B1 default) | 174 | 862 | 501 | 16 |
| Quiescent release | 174 | 704 | 343 | 16 |

After every one of those failures the test checks: the call returned false; same root
pointer; no publication, no retained-list change; no segment built, no owner or pin taken;
same chunks, same reserved bytes, same committed bytes, same writable chunk and write offset;
store content equal to the reference model; `validate()` clean. "Tolerated" are erases whose
best-effort tombstone-removal rebuild could not allocate: the erase still completed correctly.
Construction with a failing allocation is also covered (`ok()` is false, no null root is
exposed; `KVStore()` throws `std::bad_alloc`).

Observations, with their limits:

- **Reads scale with readers** where the locks did not: 14.4 → 108.5 M gets/s from 1 to 8
  readers with a paced writer (7.5×), and p99.9 stays at 0.34–0.57 µs in every configuration.
  For comparison the locks' p99.9 at 8 readers was 12.9 µs (`global_lock`) and 1.1 µs
  (`rwlock`). Different power source; treat the ratio as indicative.
- **Writes are far more expensive than under a lock.** 54,000–110,000 puts/s unthrottled
  against 0.6–2.9 million for `global_lock` in Part A: each put copies about 26 KiB and
  updates about 310–360 counters to change 32 bytes. This is the cost the blueprint accepts for
  v1 (§3.3) and it is recorded here, not optimized.
- **The writer slows as readers are added** (109,514 → 54,296 puts/s from 1 to 8 readers)
  although it takes no lock. Not investigated; candidates are memory-bandwidth and cache
  competition and, at 8 readers, sharing a physical core with a reader.
- **A reader next to a busy writer is slower than a lone reader** (8.66 vs 17.67 M/s at one
  reader). Not investigated; the writer is streaming 2–3 GiB/s of freshly allocated memory.
- The single lock-free reader (17.67 M/s) is slightly slower than Part A's unsynchronized
  single thread (18.95 M/s); the difference is within what the change of power source could
  explain and no claim is made.
- The unthrottled-writer window is 1 s here against 3 s in Part A.

100k+ RPS target: every configuration exceeds 100,000 gets/s by a wide margin, but the store
is not the finished Part B store (no reclamation), so this is not yet the Part D answer.

## Profiling bottlenecks and next hypotheses

No profiler was run in B1 (and `perf` is currently unusable again, see limitations). From the
counters only:

- The write path is dominated by copying: 23.9 KiB of slots plus 2 KiB of directory per
  32-byte update, plus about 255 atomic owner increments and 58–105 pin increments.
- Hypotheses for later, **not measured and not acted on**: a two-level directory would cut the
  per-write directory copy and owner updates (blueprint §3.3 names it as a future
  optimization); smaller partitions (more of them) would cut the segment copy; fresh
  allocation of every clone makes the writer page-fault-bound without reclamation, which B2
  changes by recycling memory.
- For readers, the next thing to measure in B2 is the cost of the epoch announcement (two
  `seq_cst` stores per `get` to a per-reader slot) against the figures above.

Deviations from the blueprint, with justification (all in `docs/decisions.md`):

1. **D-031 — `rcu` is a fourth build next to unchanged Part A variants**, rather than the
   lock variants being re-based on the copy-on-write engine. Keeps the Part A baselines exactly
   as measured and lets Part D build all four from one tree. It is an interpretation of "don't
   fork the store" and is **flagged for your confirmation**.
2. **D-034 — COW segments start at 16 slots**, not the blueprint's provisional 1024. A write
   copies the whole segment it touches; a nearly empty 1024-slot segment would cost 24 KiB per
   write. At the workload's fill the segments are 1024 slots regardless.
3. **D-034 — a Version embeds its directory** instead of pointing at a separate `Directory`.
4. **D-032 — quiescent-release hatches** exist for single-threaded tests and benchmark
   set-up. They are not in the blueprint. Without them the ownership-release code could only
   run at destruction and would be nearly untested until B2; with them it runs on every write
   of the single-threaded tests. They are unsafe with concurrent readers by construction and
   must go or be gated in B2.
5. **D-035 — `erase` can return false on allocation failure**, indistinguishable from "absent"
   through the API.
6. **Partitions that become empty are dropped** (null directory entry).
7. "Instrument probe lengths and collision counts" (blueprint §3.2) is **not done**.

Limitations:

8. **Memory grows without bound**: about 26.8 KiB retained per write at the workload's size.
   The default `rcu` driver run (100,000 trades) holds several GiB. Unusable for long
   write-heavy runs until B2.
9. Unthrottled writes are about 11–27× slower than under the global lock in Part A (54,296 vs
   601,952 puts/s at 8 readers; 109,514 vs 2,909,886 at 1 reader), with the power-source caveat.
10. One writer thread only; not enforced.
11. `set_reclaim_batch` is inert; Part B is incomplete until B2.
12. The observation set ran on battery; the Part A numbers beside it were taken on AC.
13. The machine was rebooted during this milestone; `kernel.perf_event_paranoid` is back at
    `4`, so `perf` is unusable again (informational gate `perf_stat_usable` FAIL). B1 needs no
    profiling; B2/D will. Making the setting persistent needs root
    (`/etc/sysctl.d/…`); I did not change it.
14. GCC 15.2 only.

Source ambiguities carried forward unchanged: preload-only generator; mostly-missing random
keys; partial join in the generator; **OPEN / INSTRUCTOR** exactly-one-Snapshot across two
stores (O-1). New open item O-8 = point 1 above.
