## Design decisions and invariants

### Architecture implemented

```text
key --hash_key()--> h
  partition = h & 255                         256 partitions, fixed
  segment   = segments[partition]             HashSegment: one flat slot array
  start     = (h >> 8) & (capacity - 1)       linear probing, no cross-segment probing
  slot      = { long key; ValueRef value; SlotState state }      24 bytes
  ValueRef  = { chunk_id, offset, length }
  bytes     = directory[chunk_id >> 10][chunk_id & 1023]->data() + offset
```

**Hash index (`HashSegment`).** States Empty / Occupied / Tombstone. Lookup stops at Empty,
skips Tombstone, matches on the full key. Insert scans the whole chain to the first Empty slot
before reusing a tombstone, so a key is never stored twice. Erase writes a tombstone. A
replacement array is built privately and swapped in when (a) an insert into an Empty slot
would push live + tombstones above 70 % of capacity — doubling, or same capacity when
tombstones are ≥ 20 % — or (b) an erase brings tombstones to ≥ 20 %. Segments start at 1024
slots, allocated on the first insert into the partition, and never shrink.

**Value arena (`Arena`).** 64 KiB chunks, append-only; a value never spans chunks; a value
larger than a chunk gets a dedicated chunk of its exact size; a zero-length value is the
sentinel `{0xFFFFFFFF, 0, 0}` and uses no arena space. The chunk directory is a fixed
1024 × 1024 table whose blocks are installed on demand and never freed. Stored bytes are never
overwritten while referenced: an overwrite appends and repoints the entry.

**Chunk lifetime (A1 only, D-017).** Each chunk counts the index entries that point into it.
At zero, a sealed chunk is freed, its directory slot nulled, and its ID pushed on a free stack
for reuse; the writable chunk is instead reset to offset 0. This is correct only because in
A1 no reader can hold a `ValueRef` across a writer operation. Part B replaces it with segment
pins and EBR.

**Failure atomicity.** `put` runs in this order under the write lock: (1) plan the slot,
building the replacement array if needed; (2) append the bytes to the arena; (3) commit.
Steps 1 and 2 are the only fallible ones and neither changes anything a reader can reach;
step 3 cannot fail. Free-ID stack capacity is reserved when an ID is first issued, so freeing
a chunk never allocates. `erase` needs no memory: if its tombstone-removal rebuild cannot
allocate, the erase still succeeds and the rebuild is retried later.

**Synchronization.** `get` takes the lock shared (rwlock) or exclusive (global_lock) for the
probe and the copy-out; `put`/`erase` take it exclusively. The key is hashed before the lock
is taken. `single` compiles the guards to nothing.

## Profiling bottlenecks and next hypotheses

Nothing was profiled. Things to measure in A2 rather than assume:

- `get` does three dependent memory accesses after the lock: segment slot, chunk-directory
  block, chunk bytes. Whether the directory indirection matters next to the lock cost is
  unknown.
- In debug builds `concurrent_lock_test` completed far more reads under `rwlock` than under
  `global_lock` for the same writer work. That is an unpinned, uncontrolled test run and is
  **not** a scaling result; it only suggests the A2 comparison will show a difference.
- `std::shared_mutex` on glibc prefers readers by default, so a continuously reading workload
  may starve the writer. The A2 active-writer harness should record writer throughput
  alongside reader throughput so that effect is visible.

## Known limitations and source ambiguities

Deviations from the blueprint (all recorded in `docs/decisions.md`):

1. **D-017 — chunk lifetime by per-chunk entry count, with reset of the writable chunk.** The
   blueprint describes chunk ownership only for the RCU design (segment pins). A1 needed some
   rule or updates would grow memory without bound; this is the simplest one that is correct
   under a lock. It must be replaced in Part B and the in-place reset must go.
2. **D-018 — segments are allocated lazily**, on the first insert into a partition. The
   blueprint does not say when; an empty store therefore uses no index memory.
3. **D-018 — growth rule on overflow** (double unless tombstones ≥ 20 %). The blueprint gives
   the two thresholds but not which action wins when both could apply; this choice guarantees
   at least 0.2 × capacity operations between rebuilds.
4. **D-019 — test hooks in a separate library**, and an internal inspector reachable through a
   private `friend`. The public API is unchanged.
5. **D-016** — A1 mutates in place under locks. This is what blueprint §8.3 asks for, stated
   here because the agreed architecture's immutability arrives only in Part B.

Limitations:

6. No compaction: a chunk with one live value keeps its 64 KiB (or its whole dedicated
   allocation). An adversarial pattern (one long-lived small value per chunk) can hold far more
   memory than is live.
7. Segments never shrink. After a mass erase the slot arrays keep their size.
8. A burst of keys landing in one partition pays an O(capacity) rebuild on each doubling while
   the writer holds the lock; readers wait for it in both locked variants.
9. `get` cannot report the value's length (API limitation); callers must know record sizes.
10. Maximum value 1 GiB; maximum 1,048,576 live chunks (64 GiB of ordinary values). Beyond
    either, `put` returns `false`.
11. `KVStore()` throws `std::bad_alloc` if its private state (about 22 KiB) cannot be allocated.
12. The `single` variant is unsafe for any concurrent use, including concurrent reads with a
    writer; nothing in the store enforces that.
13. Tested with GCC 15.2 only.

Source ambiguities carried forward unchanged: preload-only generator, mostly-missing random
keys, partial join in the generator, and the **OPEN / INSTRUCTOR** exactly-one-Snapshot
cross-store question (O-1), deliberately not addressed in A1 (D-015).

Unresolved for A2: FlameGraph scripts are not installed (O-3); tunables are at blueprint
defaults and unmeasured (O-6).
