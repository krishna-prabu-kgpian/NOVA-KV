## Design decisions and invariants

Architecture and ownership (full text: `docs/versioning.md`, `docs/reclamation.md`):

```text
current ──atomic──> Version { segments[256] } ──> Segment { slots[], chunk list, owners }
                                                      └─> ValueRef ─> chunk directory ─> PinnedChunk { refs, bytes }
epoch (atomic)      ReaderSlot per participant, in append-only blocks
retirement queue    FIFO of { version, retirement epoch }, writer -> cleaner
```

- **Version → Segment:** `owners` = versions pointing at the segment. Taken after the last
  fallible step of a commit; released when the cleaner processes a retired version.
- **Chunk:** `refs` = segments listing it + 1 if it is the writable chunk + 1 if an open
  commit holds it. Destroyed only by the decrement that reaches zero.
- **Reader:** announce, validate, one root load, read, clear. **Writer:** swap, tag with the
  epoch read after the swap, queue. **Cleaner:** gated advance; destroy a version only when
  the epoch is ≥ tag + 2.
- **Pass:** one advance attempt, then at most `n` versions completely destroyed, within
  `n × 1024` work units, resumable mid-version.

### Code-specific EBR safety argument

`docs/reclamation.md` §5, against labelled operations in the code (`[P1]`–`[P5]` reader,
`[W1]`–`[W3]` writer, `[C1]`–`[C6]` cleaner, `[R1]` slot-block link). It covers the ten points
required: no unprotected root (§5.1); the collector cannot overlook a pinned participant —
*bounded overtaking*, Lemma B (§5.2); an old reader prevents advancement and a version is not
destroyed early (§5.3); segment owners (§5.4); chunk references (§5.5); chunk-ID reuse and the
ID pool (§5.6); retirement records neither lost nor consumed twice (§5.7); slot registration
and thread exit (§5.8); cleanup and shutdown (§5.9); fifteen dangerous interleavings with the
mechanism and the test for each (§5.10); and what is not proved (§5.11).

It is a manual proof sketch over the `seq_cst` total order, not machine-checked, and it
assumes one writer and the shutdown contract. One sentence of the formal-safety supplement
(§4, second bullet) turned out to be too strong as written; the property that holds and
suffices is Lemma B (decision D-045). The protocol itself is implemented as specified.

Observations, with their limits:

- **The epoch announcement costs readers little here.** At 8 readers the store with
  reclamation reads as fast as the B1 checkpoint without it (44.57 vs 44.01 M/s, same session).
  For a lone reader it is about 14 % slower in the medians (6.01 vs 6.97 M/s) with overlapping
  ranges; not resolved more finely than that.
- **Memory is bounded when reclamation runs.** 17–19 MiB under an unthrottled writer for the
  whole run, against 2.27 GiB after 1.3 s with reclamation disabled. The backlog peaked at a
  few hundred versions.
- **The writer is faster than in B1 under the same conditions** (81,532 vs 24,728 puts/s at 8
  readers), plausibly because freed memory is reused instead of every clone touching fresh
  pages. Not investigated further; B1's window was also shorter (1 s).
- **Batch size made little measurable difference in this workload.** The cleaner keeps up at
  every setting, so batches of 256 and 1024 never filled (at most 232 and 230 versions in a
  pass). Batch 1 shows the expected direction: the most passes (271,658), the largest backlog
  (569) and slightly lower write throughput. Read throughput and p99.9 are within noise across
  settings, and the worst single stall (0.2–3 ms) does not follow the batch size; with 3 runs
  per setting on a loaded laptop it is dominated by scheduling. **This set does not
  demonstrate the "bigger batch, longer stall" trade-off**; Part D.2 will need a workload in
  which reclamation falls behind, and a quieter machine.
- **The stop-the-world comparator is clearly worse:** reads drop to 2.94 M/s and stall for
  about 42 ms at the median run's maximum, against 0.16–0.24 ms for epoch-based passes.
- **The cleaner is not cheap under an unthrottled writer:** 2.4–2.9 s of CPU in a 3.5 s run,
  i.e. most of one core, running 62,000–270,000 passes. With the writer paced at 10,000/s it
  uses 0.21–0.26 s (about 7 %).
- **Versus Part A in the same session** (different storage and update strategy, not only
  synchronization, D-038): 4.2× the shared-mutex store's read throughput and 9.5× the mutex
  store's at 8 readers with a paced writer, with p99.9 of 0.46 µs against 10.5 and 17.4 µs.
  Write throughput is the other way round against the mutex store (81,532 vs 284,738 puts/s
  unthrottled); the shared-mutex store starves its writer (1,852 puts/s).
- 100k+ RPS: every configuration exceeds 100,000 gets/s. The Part D statement still needs the
  D.1 protocol and comparable conditions.

## Profiling bottlenecks and next hypotheses

No profiler could be run. From counters only:

- Writes are still dominated by the copy (24 KiB of slots + 2 KiB directory per 32-byte
  value) and about 360 counter updates.
- The cleaner spends most of a core when the writer is unthrottled, largely on passes that
  each free one or a few versions; an idle threshold or adaptive pacing could cut that. **Not
  measured, not acted on.**
- Audit item R8 (ownership counters on cache lines readers load) is open. A lone reader next
  to an unthrottled writer reads 3.84 M/s against 6.01 M/s alone in this session; whether R8
  explains that needs a profiler.
- The epoch is advanced on every pass while anything is retired, which makes readers repeat
  their validation occasionally (retries are counted; their cost was not isolated).

## Known limitations and source ambiguities

Deviations from the blueprint and the supplement (all in `docs/decisions.md`):

1. **Reader slots are dynamically expandable** rather than a fixed pre-registered registry
   (user decision D-040; argued in Lemma B step 4).
2. **`get` may throw `std::bad_alloc`** on a thread's first read if a slot block cannot be
   allocated, instead of returning a value (D-042).
3. **Lemma B replaces one sentence of the supplement's proof sketch** (D-045).
4. **The cleaner attempts an epoch advance on every pass with pending work**, as the user's
   definition of a pass requires, rather than only when the oldest entry is not yet eligible.
5. **Work budget is `batch × 1024` units per pass**, so the batch size and the work budget
   scale together (D-043).
6. **Three cleaner modes** (Background, Manual, Inline); the blueprint describes only a
   background cleaner. Manual and Inline run the same protocol and exist for deterministic
   tests.
7. The reclaim-batch member is in the private implementation object (compliance note 1).
8. R8 and "instrument probe lengths" are not done.

Limitations:

9. One stalled reader or pin stops all reclamation; memory then grows without bound and
   writes eventually fail on allocation. No backlog limit (by decision).
10. Writes cost far more than under a lock; the cleaner uses most of a core under an
    unthrottled writer.
11. "Bounded pause" is bounded work per pass, not a wall-clock bound.
12. Registration scans the slot list linearly; with tens of thousands of simultaneously
    registered participants this becomes slow (an `epoch_test` case with about 9,000 slots
    takes seconds under TSan).
13. Exactly one writer thread; not enforced. Readers and pins must be gone before the store is
    destroyed; not enforced.
14. The safety argument is manual; the measurements are 3 repetitions on battery with the
    `powersave` governor and no profiler.
15. GCC 15.2 only.

Source ambiguities carried forward: preload-only generator; mostly-missing random keys;
partial join in the generator; **OPEN / INSTRUCTOR** exactly-one-Snapshot across two stores.

Environment: the power source and governor were changed outside this work between
milestones. No `sudo` and no kernel setting were used or changed.
