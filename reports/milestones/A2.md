## Design decisions and invariants

Recorded in `docs/decisions.md`:

- **D-024 measurement method.** Two tracks never mixed: the unmodified generator
  (preload-only) and the project harness (writer active). 0.5 s warm-up, 3 s window, loading
  excluded; 5 separate processes per configuration; median with min–max; no run discarded;
  threads pinned (readers one per physical core, fast cores first; writer on CPU 15).
- **D-025 flame graphs.** `perf record -F 1999 --call-graph fp` on cycles; widths are shares of
  CPU cycles; on-CPU only. Kernel frames have no symbols here and are merged into one
  `[kernel]` frame; raw `perf script` output kept.
- **D-026 layout benchmark.** Same data, same access sequences, direct addressing, cross-layout
  checksum must match.
- **D-028 layout decision: NSM.**
- **D-029** the first campaign was discarded because the power source changed during it.
- **D-023 (user)** the A1 chunk lifetime scheme must be redesigned in Part B.

Validity checks built into the harness (a run exits nonzero otherwise): the writer completed at
least one successful update inside the measured window; no read returned a record for another
key; every key that should exist was found; no writer update failed; the store's structural
invariants hold after the run; every thread was pinned. All 90 measured runs exited 0.

## Profiling bottlenecks and next hypotheses

Measured, for the lock-based store:

- A single lock word is the bottleneck in both variants at 8 readers: through blocking for
  the mutex, through cache-line transfers for the shared mutex.
- The index probe and copy are 2–9 % of cycles in every profiled configuration; the data
  structure is not what limits Part A.

Hypotheses for Part B, **not measured**:

- Removing the shared lock word from the read path should remove both effects; per-reader
  epoch slots must then be cache-line isolated or the bouncing will simply move there.
- `KVStore::Impl` places the lock directly before the segment array, so the lock's second
  cache line also holds metadata of the first partitions. Not separated in Part A.
- Arena payloads are not cache-line aligned; about half of the 32-byte rows straddle two
  lines (D-028). Candidate optimization, to be measured.

## Known limitations and source ambiguities

Deviations from the blueprint:

1. **A second writer setting** (paced, 10,000 updates/s) was measured in addition to the
   continuous writer §9.1 describes. The rate is our choice.
2. **Three layouts** instead of the required two, and the benchmark addresses records directly
   rather than through a hash index, to isolate the layout (D-026).
3. **Durations.** 3 s windows (2 s for the preload-only runs) rather than the generator's
   default 5 s, to keep 135 runs within a practical campaign length and the generator's
   per-sample memory bounded.
4. **Latency histogram instead of raw per-operation samples** in the harness (blueprint §9.3
   allows histograms with the maximum preserved).
5. `perf c2c` was added beyond what §8.4 lists as mandatory ("if available").

Limitations of the evidence:

6. One machine, a laptop with a desktop session running; heterogeneous cores; with 8 readers
   the eighth shares a physical core with the writer. 4 → 8 readers is not a like-for-like
   doubling.
7. The writer's rate is a free parameter and changes the picture completely; only two points
   were measured.
8. Timing each `get` with two clock reads is part of every measured operation.
9. Kernel frames are unsymbolized (`kptr_restrict = 1`). Kernel time is attributed to its
   user-space caller only.
10. Flame graphs are on-CPU; blocked time is invisible in them.
11. `perf c2c` shares come from one 5 s run per configuration with 100–3,482 HITM samples.
12. The interpretation that the clock read absorbs lock-word wait time in the 8-reader
    `rwlock` profile is an inference.
13. The PAX scan result reflects this benchmark's per-access page arithmetic.
14. Maximum latencies of 0.1–5.4 ms were observed and not attributed.
15. The tunables (partition count, segment capacity, chunk size) were not swept.
16. The first campaign was discarded (D-029); only the rerun is reported.

Source ambiguities carried forward unchanged: preload-only generator, mostly-missing random
keys, partial join in the generator, and the **OPEN / INSTRUCTOR** exactly-one-Snapshot
cross-store question (O-1).

Environment notes: the governor (`powersave` → `performance`), the power source and the
installation of cmake, pandoc and TeX Live were changed by the user during this milestone. The
agent used no `sudo` and changed no kernel setting.
